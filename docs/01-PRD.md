## 1. 产品定义

### 1.1 一句话

**一个人用的跨境电商研究工作台**：把「想卖什么、去哪卖、能不能赚」这件事，拆成可执行的任务，交给固定的 Agent 角色产出草稿，人只做判断与确认，结论与来源一起沉淀。

### 1.2 它解决什么问题

| 问题 | 现状（没有这套系统时） | 系统里的对应能力 |
|---|---|---|
| 研究过程散 | 浏览器标签、微信收藏、Excel 各存一份，三天后找不到 | 项目 + 任务 + 知识库 + 文件中心，全部落 PostgreSQL |
| 结论没有来源 | 「听说这个品能卖」——听谁说的、什么时候说的，查不到 | 报告级来源登记（标题/链接/摘录/数据类型），导出自动带附录 |
| 数据不落盘 | 算完就关页面，换个售价重算一遍 | 财务方案入库 + 多售价对比 + 保本线图 + 计算接口 |
| AI 调用不可控 | 不知道花了多少钱、产出算不算数 | 未接模型时明确产出「研究框架」并标注；执行记录区分框架/模拟/真实模型 |
| 决策不可追溯 | 当时为什么定 19.9，没人记得 | 审计日志 + 数据类型（R/E/P/S/U）+ 里程碑 |

### 1.3 它不是什么

- **不是 SaaS**：没有注册、没有多租户、没有计费。单用户本地运行，数据在本机。
- **不是自动选品工具**：不抓平台数据、不预测爆款。它组织研究过程，不替代研究本身。
- **不是店铺后台**：不做订单、库存、上架、广告投放、客服。这些在「明确不做」里。
- **不是 AI 结论生成器**：当前版本未接模型，Agent 产出的是研究框架（要回答的问题、要核对的项），不是结论。

### 1.4 目标用户

**第一阶段只有一个用户**：准备做或刚开始做跨境电商的个人创业者。

- 有明确的启动预算（几万元量级），亏不起一次选品失误
- 会自己查资料，但缺一套「查完之后放哪、怎么复核」的方法
- 不写代码，能照着 README 装好 Node 与 PostgreSQL
- 主要在 Windows 笔记本上使用，屏幕 1440 宽；偶尔用手机看进度

### 1.5 使用场景

**场景 A · 从零评估一个品类**

> 「想在亚马逊美国站卖宠物冻干零食，预算 5 万，能不能做？」

在 AI 总管家输入这句话 → 系统按内置流程拆成 4–6 条任务（市场、平台、选品、财务，缺角色的环节标人工）→ 勾选「拆完直接派发」→ 有 Agent 的任务立刻跑完，产出研究框架 → 首页看到「4 条执行完等你确认」→ 逐条确认或退回 → 结论写进报告 → 登记来源 → 导出 .md 存档。

**场景 B · 定价决策**

> 「采购 6 元、运费 2.5 元、佣金 15%，卖 19.9 美元还是 24.9？」

财务模拟建方案 → 看单件净利、毛利率、保本单量 → 多售价对比看五档 → 保本线图标出保本价与当前价 → 改基准价，五档与图实时重算 → 选定价格写进报告。

**场景 C · 中断后继续**

> 工作流跑到第 13 个节点（人工闸门），今天不想批。

关掉页面，第二天打开工作流中心 → 看到运行停在哪、哪些节点已完成 → 批准 → 继续跑到报告归档；如果中间某个节点失败，可以只重试失败节点，前序产出复用，不从头再跑。

## 2. 开发总原则（不可违反）

1. 先工程结构，后业务功能
2. 先数据库与基础架构，后复杂 Agent
3. 先单人本地，后云端企业部署
4. 先打通一条完整业务流程，后扩展模块
5. 所有数据持久化，不能只存在前端页面
6. 所有功能真实可用，静态页面不冒充功能
7. AI 必须通过受控接口调用工具
8. 所有重要操作留日志
9. 数据库变更必须通过迁移文件
10. 所有开发工作有测试与验收记录

> 这十条不是口号，落地方式见第 8 节「数据与规则」与第 10 节「验收标准」。

## 3. 功能范围总览

### 3.1 信息架构

```
总览   AI 总管家 · 综合首页
执行   项目中心 · 任务中心 · Agent 中心 · 工作流中心 · 执行记录
```

## 5. 核心业务流程

### 5.1 从目标到交付（主链路）

```
输入目标
  → 拆解（规则模板，标注来源）
  → 建任务（有 Agent 的分配，没有的标人工）
  → 派发执行（单条失败不中断）
  → 产出落到 agent_runs / agent_messages
  → 任务转 review（待确认）
  → 人工确认
      ├─ 确认 → 任务 done → 结论进知识库 / 报告
      └─ 退回 → 补验收标准 → 重跑（复用前序）
  → 报告登记来源（citations）
  → 导出 .md / 打印 PDF
```

**关键约束**：执行成功 ≠ 任务完成。系统只把任务推进到 `review`，`done` 必须由人点。

### 5.2 工作流链路

```
选流程 → 启动 → 逐节点推进
  ├─ 普通节点：执行 → 写产出 → 继续
  ├─ 人工闸门：停下，等人 approve / reject
  ├─ 失败：运行转 failed，可 retry（重试该节点）或 skip（须写原因）
  └─ 结束：报告归档 → 知识库写入
```

### 5.3 数据沉淀链路

```
任务产出 → 执行记录（全文可查）
        → 知识库（工作流归档）
        → 报告（正文 + 来源）
        → 导出文件（.md / PDF）
```

## 6. 数据与规则

### 6.1 数据类型（R/E/P/S/U）

| 标记 | 含义 | 使用要求 |
|---|---|---|
| R | 真实数据 | 有可复核来源，优先使用 |
| E | 估算数据 | 必须写明估算依据 |
| P | 预测数据 | 必须写明预测方法与假设 |
| S | 模拟数据 | 仅用于演示，不得作为决策依据 |
| U | 用户输入 | 未经核实的个人判断 |

规则：没有来源的结论不得作为决策依据；导出时数据类型随来源清单一并打印。

### 6.2 金额与费率

- 金额一律 `numeric(18,4)`，禁止浮点存货币
- 费率按百分数存（`15` 表示 15%），计算时统一除以 100
- 计算结果保留 4 位小数，与数据库口径一致

### 6.3 权限与审批

| 等级 | 能力 | 是否需要审批 |
|---|---|---|
| L1 | 读取、检索 | 否 |
| L2 | 生成草稿、计算、建任务 | 否 |
| L3 | 对外发送、修改外部系统、花钱 | 是 |
| L4 | 自动执行高风险动作 | 系统禁止 |

### 6.4 日志

所有重要操作写 `audit_logs`：创建、修改、删除、执行、审批、导出、来源登记。日志包含操作人、实体、动作、权限等级与关键参数。
